# WorkShield MVP 통합 검증 문서

## 1. 문서 목적

WorkShield MVP의 업로드부터 계약 유형 선택, 검토 진행, 결과·법령 근거·협의문구·챗봇까지의 전체 흐름을 실제 웹앱에서 검증한다.

기준 문서:

- `docs/requirements/archive/요구사항.json`
- `docs/requirements/요구사항.md`
- `docs/splint/1차 구현범위 검증 목록.md`
- `docs/splint/운영 검증 목록.md`
- `docs/splint/LLM 검증.md`

## 2. 실행 환경 기준

| 구분 | 기준 |
|---|---|
| 개발·통합 검증 담당자 환경 | Ollama |
| 발표 시연 기준 | vLLM + RunPod |
| API·MCP | 발표 시연 환경 설정에 따름 |
| 데이터 | 세션 기반 임시 데이터, 30분 TTL |
| 검증 대상 | 프로젝트 발표 시연용 웹앱 및 연결된 API |

통합검증 담당자는 Ollama로 실제 웹앱의 기능 흐름을 검증한다. 발표 시연 환경은 vLLM + RunPod를 기준으로 별도 확인한다. 두 환경의 모델명·응답시간·구조화 출력 결과를 동일하다고 간주하지 않는다.

## 3. 공통 기록 기준

각 케이스마다 다음을 기록한다.

```text
케이스 ID
실행일
웹앱 URL
파일명
review_id
세션 ID
선택 계약 유형
HTTP status
실제 API 응답 상태
결과(PASS/FAIL)
오류·특이사항
증빙 링크 또는 캡처
담당자
```

법령·협의문구·챗봇 케이스에는 다음 응답 필드를 추가로 기록한다.

```text
grounding_status
sources.LAW
outcome
answer 또는 text
required_confirmations
tool_status
retryable
next_action
```

> `sources.LAW`는 법령 조회 결과가 있는 경우에만 기대한다. 법령 조회 실패·미조회 상태에서는 법령을 임의 생성하지 않고 상태와 안내를 확인한다.

## 4. 3가지 계약 유형 검증

### 공통 기준

- 허용 유형은 `SW_FREELANCE`, `SI_SUBCONTRACT`, `SM_SUBCONTRACT`만 사용한다.
- 추천 유형과 사용자 최종 선택 유형을 구분한다.
- `CONTRACT_TYPE_UNCERTAIN`에서는 유형 선택 전 검토를 시작하지 않는다.
- `OUT_OF_SCOPE`에서는 명시적 재확인 전 검토를 시작하지 않는다.
- 최종 결과는 위법·합법·유리·불리 같은 법적 결론이 아닌 검토 후보로 표시한다.

### 정상 케이스

| ID | 시나리오 | 기대 결과 |
|---|---|---|
| CT-N-01 | `SW_FREELANCE` 선택 | 선택값이 세션과 검토 요청에 저장됨 |
| CT-N-02 | `SI_SUBCONTRACT` 선택 | 선택값이 세션과 검토 요청에 저장됨 |
| CT-N-03 | `SM_SUBCONTRACT` 선택 | 선택값이 세션과 검토 요청에 저장됨 |
| CT-N-04 | 추천과 다른 유형 선택 | 추천값과 최종 선택값이 분리 저장됨 |
| CT-N-05 | 유형 변경 후 검토 | 최종 선택 유형 기준으로 검토됨 |

### 오류·경계 케이스

| ID | 시나리오 | 기대 결과 |
|---|---|---|
| CT-E-01 | 유형 미선택 진행 | 검토 API 호출 없이 선택 요구 |
| CT-E-02 | 허용 목록 밖 유형 전달 | 4xx 및 재선택 안내 |
| CT-E-03 | `OUT_OF_SCOPE` 재확인 없이 진행 | 검토 API 호출 차단 |
| CT-E-04 | 후보 누락·null·빈 배열 | 자동 확정하지 않고 직접 선택 유도 |
| CT-E-05 | 세션 토큰 불일치 | 다른 세션 결과 비노출 |
| CT-B-01 | 후보 동점 | 자동 확정하지 않고 사용자 선택 요구 |
| CT-B-02 | 혼합 계약 표현 | 사용자 최종 선택 유형 기준으로 검토 |
| CT-B-03 | 동일 파일을 다른 유형으로 연속 검토 | `review_id`별 결과가 섞이지 않음 |

## 5. 업로드 검증

### 정상

- PDF, HWP, HWPX, DOCX 업로드
- 최대 허용 크기 파일 업로드
- 한글·공백·특수문자 파일명
- 업로드 진행 상태와 검토 진행 상태 구분

### 오류·경계

- 확장자 없음·미지원 형식
- 확장자와 실제 형식 불일치
- 손상·암호화·빈 문서
- 10MiB 초과·정확히 10MiB·10MiB 직전 파일
- 스캔 PDF 등 텍스트 추출 불가 문서
- `file_path` 또는 `file_content + file_name` 입력 계약 위반
- 업로드 네트워크 오류·413·429·503·504

기대 결과:

- 오류 코드별 안내
- 413과 429 구분
- 실패 후 파일·계약 유형 유지
- 자동 재시도 없이 사용자가 재시도
- 빠른 클릭·연속 drop에도 POST 1건만 발생
- 비 JSON proxy 오류의 원문·스택 트레이스 미노출

## 6. 검토 진행·SSE

### 정상 흐름

```text
업로드
→ 계약 유형 선택
→ review_id 생성
→ QUEUED
→ REVIEWING
→ COMPLETED
→ 결과 확인
```

검증 항목:

- 진행 이벤트 또는 상태 응답에 검토 식별자와 진행 상태가 연결된다.
- SSE를 사용하는 경우 이벤트에 `review_id`, `sequence`, `stage`, `percent`, `message`가 포함되는지 확인한다.
- 정상 SSE 연결에서는 progress 이벤트가 늦어도 polling을 시작하지 않는다.
- 최초 REST 상태 조회는 1회만 실행한다.
- SSE 연결 오류가 발생한 경우에만 fallback polling을 실행한다.
- fallback polling은 최대 1개만 실행한다.
- SSE가 복구되면 polling timer와 실행 중 요청을 정리한다.
- SSE와 REST 응답이 교차해도 오래된 `sequence`는 반영하지 않는다.
- 진행률과 단계가 역행하지 않는다.
- 완료·실패·취소·만료 후 EventSource·timer·HTTP 요청이 남지 않는다.
- 화면 이탈·`review_id` 변경 후 이전 이벤트가 반영되지 않는다.

### 오류·경계

- SSE 연결 강제 종료
- EventSource 자동 재연결
- SSE 정상 무이벤트
- REST·SSE 교차 응답
- 이전 검토의 늦은 이벤트
- 진행률 역행
- 동시 검토 초과
- 서버 재시작 중 진행 중 검토

## 7. 결과·법령·협의문구 검증

### 결과 표시

- `NONE`, `EXTRA`, `NO_MATCH`, `MISSING`을 구분한다.
- `MISSING`은 별도 체크리스트로 표시한다.
- 최상위 상태가 오류이면 빈 배열을 문제 없음으로 해석하지 않는다.
- `toxic_patterns`는 결과 상태와 독립적으로 표시한다.

### 법령·협의문구 조합

| ID | 법령 | 협의문구 | 기대 결과 |
|---|---|---|---|
| LG-01 | 있음 | 있음 | 법령명·조문과 협의문구가 표시됨 |
| LG-02 | 있음 | 없음 | `outcome`, `text`, `required_confirmations`로 실패 원인을 확인함 |
| LG-03 | 없음(`NO_RESULT`/`UNMAPPED_CATEGORY`) | 있음 | 법령 부재로 단정하지 않고 조항 근거 문구를 표시함 |
| LG-04 | 없음(`TIMEOUT`/`UPSTREAM_ERROR`) | 없음 | MCP 상태와 Suggestions 실패를 구분함 |

확인 기준:

- MCP 성공 시 `sources.LAW`가 최종 챗봇 응답에 포함된다.
- MCP 실패 시 법령을 추측하지 않고 상태와 제한사항을 반환한다.
- 사용자·표준 조항 근거가 있으면 법령 실패만으로 협의문구를 차단하지 않는다.
- `GENERATED`이면 `text`가 비어 있지 않다.
- `REQUIRED_VALUE_MISSING`이면 필요한 확인 항목을 표시한다.
- `LLM_OUTPUT_INVALID`이면 빈 결과를 성공으로 표시하지 않는다.

## 8. 챗봇 검증

### 정상·오류·경계

- 현재 계약서·검토 결과·연결 법령 범위 질문
- 법령 근거 질문
- 검토 결과와 무관한 질문
- 법률 결론 요구
- MCP 조회 실패
- 근거 없는 문구 생성 요청
- 문서 내 프롬프트 인젝션
- 존재하지 않는 조항 ID·법령 식별자
- 계약서에 없는 금액·기간·비율

기대 결과:

- 현재 검토 근거 밖 질문은 `REFUSED` 처리
- 실제 검토·법령 출처만 반환
- 법률 결론을 단정하지 않음
- 프롬프트 인젝션을 실행하지 않음
- 근거 없는 수치·출처를 생성하지 않음

### 세션 초기화

- 새 검토 시작 시 messages·입력값·오류·focus·history 초기화
- `review_id` 변경 시 이전 대화 미표시
- 검토 폐기 시 챗봇 닫기 및 대화 제거
- 세션 만료 시 챗봇 초기화 및 새 검토 안내

## 9. LLM 실행 환경 검증

### 통합검증 담당자 환경 — Ollama

- Ollama 정상 연결
- 모델 응답 생성
- 연결 실패·timeout
- 구조화 출력 파싱 실패
- 빈 답변 200 방지

Ollama 검증 결과를 배포 환경의 vLLM + RunPod 동작과 동일하다고 간주하지 않는다. 모델별 성능 비교는 이 통합검증의 범위가 아니다.

### 발표 시연 환경 — vLLM + RunPod

- 배포 모델 ID·provider·artifact를 기록한다.
- JSON Schema structured output을 사용한다.
- thinking OFF, temperature 0, top_p 1, seed를 고정한다.
- 운영 Suggestions 출력 상한과 timeout을 확인한다.
- 모델 응답·repair·timeout 비율을 기록한다.
- 법률 결론·허위 수치·내부 ID·허용되지 않은 source key를 차단한다.
- 발표 전 확인에서 vLLM + RunPod 경로를 별도로 검증한다.

## 10. 세션·보안·삭제

- 유효한 세션만 파일·결과·챗봇을 조회한다.
- 다른 세션 토큰으로 접근할 수 없다.
- API key와 계약서 원문·대화·프롬프트가 로그에 남지 않는다.
- 완료·실패·만료·취소 후 임시 파일을 정리한다.
- 일반 조회·질문·화면 이동으로 세션 TTL이 자동 연장되지 않는지 확인한다.
- 연장 버튼 요청 시 세션·현재 review·Cookie 만료가 현재부터 30분으로 재설정되는지 확인한다.
- 만료된 세션은 연장되지 않고 새 검토 안내로 연결되는지 확인한다.
- 진행 중 새 검토 확정 시 삭제 API가 즉시 호출되고 대기 작업 또는 로컬 stdio MCP 실행이 중단되는지 확인한다.
- 서버 재시작 후 orphan 파일과 중단 작업을 정리한다.
- `database is locked`, SQLite WAL, Uvicorn worker 1개, MCP 프로세스 1개를 확인한다.

## 11. 제한 큐·운영 검증

- 전체 검토 실행 1건·대기 5건
- Suggestions 실행 1건·대기 5건
- 업로드·범위 판별 동시 2건
- 초과 시 429와 `Retry-After`
- 취소 시 큐 자리와 실행 슬롯 반환
- 재시작 후 `QUEUED` 작업 복구
- 메모리·swap·디스크·SQLite lock·MCP/LLM timeout·HTTP 5xx 기록
- SSE 연결 수 제한 및 재연결 확인

## 12. 최종 통합 시나리오

```text
웹앱 접속
→ 파일 업로드
→ 계약 유형 확정
→ 검토 시작
→ SSE 진행 확인
→ 결과 표시
→ 법령 근거 확인
→ 협의문구 생성
→ 챗봇 질문
→ 새 검토·폐기·세션 만료 초기화
```
