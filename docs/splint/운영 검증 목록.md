# 운영 검증 목록

> 대상: S3·CloudFront 웹, 단일 EC2의 API·MCP, 외부 RunPod GPU로 구성한
> WorkShield MVP 운영 환경
>
> 기준 인스턴스: EC2 `t3.small`(2 vCPU, 2 GiB), API·MCP 각 단일 프로세스
>
> 이 문서의 수치는 부하 시험 전 초기 안전값이다. 최대 수용량은 실제 운영과 같은
> EC2·EBS·CloudFront·RunPod 환경의 부하 및 장시간 시험 결과로 확정한다.

## 1. 확정 운영 결정

| 항목 | 결정 |
| --- | --- |
| SPA fallback | S3 기본 behavior에만 CloudFront Function rewrite 적용 |
| viewer TLS | CloudFront 기본 도메인과 기본 인증서 사용 |
| origin TLS | origin용 도메인과 공인 인증서를 마련하고 HTTPS only 적용 |
| origin 접근 제한 | CloudFront prefix list 보안 그룹과 비밀 origin header 검증을 함께 적용 |
| EC2 사양 | `t3.small`(2 vCPU, 2 GiB) |
| 임시 파일 삭제 | 정상 가동 중 만료 후 최대 60초 이내, 비정상 종료·정지 후 다음 기동 시 정리 |

origin용 도메인은 CloudFront viewer 주소와 별개로 둘 수 있다. 사용자는
CloudFront 기본 도메인으로 접속하고, CloudFront는 공인 인증서가 설치된 origin
도메인으로 EC2에 HTTPS 연결한다.

## 2. 초기 운영 한도

| 항목 | 초기값 | 초과 시 동작 | 확정 상태 |
| --- | ---: | --- | --- |
| 안내용 동시 이용자 | 10명 | 혼잡 안내 | 부하 시험 필요 |
| 동시 일반 접속·조회 | 20명 | `429` 또는 짧은 재시도 | 부하 시험 필요 |
| 동시 파일 업로드 | 2건 | `429` + `Retry-After` | 구현 필요 |
| 실행 중 전체 계약 검토 | 1건 | 제한 큐로 이동 | 구현 필요 |
| 전체 계약 검토 대기열 | 5건 | `429` + `Retry-After` | 구현 필요 |
| 실행 중 LLM 문구 생성 | 1건 | 제한 큐로 이동 | 구현 필요 |
| LLM 문구 생성 대기열 | 5건 | `429` + `Retry-After` | 구현 필요 |
| 동시 SSE 연결 | 20개 | 폴링 복구 안내 | 부하 시험 필요 |
| 세션당 active review | 1건 | 기존 중복 검토 오류 유지 | 구현됨 |
| 최대 업로드 크기 | 10 MiB | `413` | 구현됨 |

초기 처리량 목표는 전체 계약 검토 분당 1~2건이다. 과거 정상 문서 평균
처리시간 19.1초는 참고값일 뿐 현재 운영 경로의 동시 부하 성능을 증명하지
않는다. Qwen 검증도 A40 한 장, 동시성 1에서만 수행했으므로 동시 생성 수를
바로 늘리지 않는다.

`t3.small`을 사용하더라도 아래 동시성은 부하 시험 전까지 확대하지 않는다.
추가 메모리는 안전 여유로 사용하고, 검토·LLM 동시성 증가는 측정 결과로
결정한다.

## 3. 배포 전 필수 구현

### 3.1 제한 큐와 과부하 제어

상세 설계와 구현 순서는
[제한 큐 및 과부하 제어 구현 계획](제한%20큐%20및%20과부하%20제어%20구현%20계획.md)을
따른다.

- [ ] 요청마다 무제한 `asyncio.create_task()`를 만드는 방식을 제한 큐로 바꾼다.
- [ ] SQLite의 `QUEUED` 상태를 작업 원장으로 사용하고 단일 review worker가
      하나씩 가져간다.
- [ ] review worker 수를 1로 고정한다.
- [ ] 검토 대기열 크기를 5로 제한한다.
- [ ] LLM 생성 동시성을 1, 대기열을 5로 제한한다.
- [ ] 업로드 동시성을 2로 제한한다.
- [ ] 큐가 가득 차면 작업을 접수한 것처럼 응답하지 않고 `429`와
      `Retry-After`를 반환한다.
- [ ] 재시작 후 `QUEUED`·`REVIEWING` 작업의 복구 정책을 검증한다.
- [ ] 취소된 작업이 실행 슬롯과 큐 자리를 즉시 반환하는지 검증한다.

단순 `Semaphore`만 사용하면 대기 Task가 계속 생성될 수 있다. 반드시 큐
자체에 최대 길이를 둔다.

### 3.2 업로드와 메모리

- [ ] reverse proxy에서 요청 본문을 12 MiB 이하로 제한한다.
- [ ] 애플리케이션의 10 MiB 제한과 proxy 제한의 오류 응답을 확인한다.
- [ ] 파일 전체를 Python 메모리에 적재하는 현재 경로를 디스크 스트리밍 방식으로
      전환할지 결정한다.
- [ ] 운영 HTTP 전송에서 발생하는 base64 복사본의 순간 메모리를 측정한다.
- [ ] 동시 업로드 2건과 검토 1건이 겹쳐도 메모리 사용률이 80% 미만인지 확인한다.
- [ ] 파일명, 확장자, 실제 형식, 암호화·손상 파일 검증을 회귀 시험한다.

### 3.3 SSE

- [ ] 세션당 SSE 연결을 1개로 제한한다.
- [ ] 전체 SSE 초기 상한을 20개로 둔다.
- [ ] 현재 1초인 SQLite 상태 조회 주기를 2~3초로 조정한다.
- [ ] `EventSourceResponse`의 heartbeat 간격을 15~20초로 명시하고 실제 운영
      경로에서 전송되는지 확인한다.
- [ ] Nginx/Caddy의 response buffering과 proxy cache를 비활성화한다.
- [ ] CloudFront origin response timeout보다 짧은 간격으로 데이터를 전송한다.
- [ ] `Last-Event-ID`, Cookie, `Cache-Control: no-store` 전달을 검증한다.
- [ ] 강제 연결 종료 후 SSE 재연결과 HTTP 폴링 복구를 검증한다.
- [ ] 정상 SSE 연결에서 progress가 20초 이상 없더라도 이벤트 미수신만으로
      REST 폴링을 시작하지 않는지 검증한다.
- [ ] HTTP 폴링은 SSE 연결 오류가 확인된 동안에만 하나를 실행하고, SSE
      `onopen` 후 예약된 타이머와 실행 중 요청을 취소하거나 무효화한다.
- [ ] SSE 재연결과 HTTP 응답이 교차하는 경우에도 두 경로가 장시간 중첩되지
      않고 progress sequence가 역행하지 않는지 검증한다.

### 3.4 SQLite와 프로세스

- [ ] Uvicorn worker를 1개로 고정한다.
- [ ] MCP 서버도 단일 프로세스로 실행한다.
- [ ] 여러 컨테이너가 API SQLite 파일을 동시에 열지 않도록 한다.
- [ ] `database is locked` 발생 횟수를 메트릭으로 수집한다.
- [ ] 검토 진행 이벤트와 TTL 갱신이 겹치는 부하 시험을 수행한다.
- [ ] SQLite와 업로드 디렉터리가 영속 EBS에 올바르게 mount되는지 확인한다.
- [ ] 종료 시 WAL·DB 정합성과 진행 중 review 복구를 검증한다.

## 4. CloudFront·네트워크 검증

- [ ] 기본 behavior `/*`는 비공개 S3 bucket과 OAC로 연결한다.
- [ ] `/api/*`, `/health/*`는 EC2 reverse proxy origin으로 연결한다.
- [ ] API behavior의 cache를 완전히 비활성화한다.
- [ ] API의 모든 HTTP method와 `OPTIONS` 전달을 확인한다.
- [ ] Cookie, query string, `Idempotency-Key`, `Last-Event-ID`,
      `X-Request-ID`, `Content-Type` 전달을 확인한다.
- [ ] `Set-Cookie`가 변형되거나 캐시되지 않는지 브라우저에서 확인한다.
- [ ] SPA 새로고침은 기본 S3 behavior에만 연결한 CloudFront Function으로
      확장자 없는 경로를 `/index.html`로 rewrite한다.
- [ ] distribution 전체의 403·404를 `/index.html` 200으로 바꾸지 않는다.
      API가 소유권 은폐에 사용하는 404까지 HTML 200으로 변환될 수 있다.
- [ ] EC2 origin에 고정 주소를 사용한다.
- [ ] EC2 inbound는 CloudFront origin-facing prefix list로 제한한다.
- [ ] CloudFront가 넣는 비밀 origin header를 reverse proxy에서 검증해 다른
      CloudFront 배포를 통한 origin 접근도 차단한다.
- [ ] EC2에 고정된 origin용 도메인을 연결한다.
- [ ] origin domain과 일치하는 공인 인증서를 reverse proxy에 설치하고 자동
      갱신한다.
- [ ] CloudFront origin protocol policy를 `HTTPS only`로 설정한다.
- [ ] 인증서 불일치·만료 시 배포 또는 운영 경보가 발생하는지 검증한다.
- [ ] API·MCP 컨테이너 포트는 host 외부에 직접 공개하지 않는다.
- [ ] SSH를 닫고 SSM Session Manager로 운영 접속한다.
- [ ] CloudFront 기본 도메인에서 웹, Cookie, SSE가 같은 origin으로 동작하는지
      실제 브라우저로 확인한다.

Docker Compose 내부에서 API의 MCP 주소는 `localhost`가 아니라 서비스 DNS를
사용한다.

```dotenv
WORKSHIELD_MCP_TRANSPORT=streamable_http
WORKSHIELD_MCP_URL=http://mcp:8000/mcp
```

API는 MCP health check가 성공한 뒤 시작하고, MCP 준비 실패 시 ready check가
성공해서는 안 된다.

## 5. 저장소와 데이터 수명주기

- [ ] EBS 암호화를 활성화한다.
- [ ] MCP 정적 corpus와 사용자 임시 데이터를 논리적 또는 물리적으로 분리한다.
- [ ] 사용자 업로드·SQLite 결과·대화 데이터는 snapshot과 AMI에서 제외한다.
- [ ] 세션의 마지막 유효 활동 후 30분 TTL을 검증한다.
- [ ] 진행 중 review의 만료 유예와 완료 후 TTL 재개를 검증한다.
- [ ] 취소·비재시도 실패·만료 시 원본 파일 삭제를 검증한다.
- [ ] tombstone 24시간 경과 후 완전 삭제를 검증한다.
- [ ] 서버 비정상 종료 뒤 orphan 파일 정리를 검증한다.
- [ ] 디스크 사용률 70%에서 경고하고 85%에서 신규 업로드를 중단한다.
- [ ] 계약서·조항·프롬프트·결과·대화 본문이 로그에 남지 않는지 확인한다.

삭제 보장은 다음 운영 문구를 기준으로 한다.

> 정상 가동 중 만료 후 최대 60초 이내 삭제하며, 비정상 종료 또는 정지 후에는
> 다음 기동 시 즉시 정리한다.

현재 최대 파일 크기를 기준으로 임시 저장소 상한은 다음 식으로 산정한다.

```text
필요 임시 용량
= 10 MiB × TTL 동안 생성 가능한 최대 세션 수
+ SQLite 결과
+ 작업 중 복사본
+ 최소 30% 여유 공간
```

## 6. RunPod 검증

### 6.1 Embedder·Reranker

- [ ] warm 상태와 cold 상태를 분리해 전체 검토 latency를 측정한다.
- [ ] RunPod timeout 180초 동안 API 작업 슬롯이 고갈되지 않는지 확인한다.
- [ ] 동일 문서 동시성 1, 2에서 GPU 메모리와 queue 동작을 측정한다.
- [ ] 외부 timeout·오류 시 review가 재시도 가능한 실패로 종료되는지 확인한다.
- [ ] 시연 전 worker 또는 Pod warm-up 절차를 작성한다.

### 6.2 Qwen3.5 9B

- [ ] thinking OFF를 유지한다.
- [ ] 운영 `max_completion_tokens=512`를 유지한다.
- [ ] JSON Schema structured output과 hard gate를 유지한다.
- [ ] 구조·언어 오류 repair를 최대 1회로 제한한다.
- [ ] 동시성 1의 기존 결과를 운영 기준선으로 사용한다.
- [ ] 동시성 2·4는 별도 시험을 통과하기 전 운영에 적용하지 않는다.
- [ ] cold start, 30분 soak, timeout, repair 비율을 측정한다.
- [ ] 모델 revision, tokenizer hash, vLLM image digest를 고정한다.

## 8. 부하 시험

운영과 동일한 EC2, Docker 이미지, EBS, CloudFront, RunPod endpoint에서 수행한다.

### 8.1 시나리오

- [ ] 일반 조회 사용자 10명, 20명, 30명
- [ ] SSE 10개, 20개, 30개
- [ ] 정상 SSE에서 progress가 20초 이상 없는 구간과 HTTP 폴링 미발생
- [ ] SSE 재연결과 실행 중 HTTP 폴링 응답이 교차하는 구간
- [ ] 10 MiB 업로드 1건과 2건 동시 실행
- [ ] 전체 검토 1건 실행 중 5건 대기
- [ ] 전체 검토와 LLM 문구 생성 동시 실행
- [ ] RunPod cold start 중 조회·SSE 유지
- [ ] 30분 이상 지속 부하
- [ ] 서버 재시작, 네트워크 단절, RunPod timeout

### 8.2 1차 통과 기준

- [ ] 메모리 사용률 80% 미만
- [ ] swap 지속 증가 없음
- [ ] OOM·컨테이너 재시작 없음
- [ ] SQLite lock 오류 0건
- [ ] MCP·LLM timeout 1% 미만
- [ ] HTTP 5xx 1% 미만
- [ ] review queue 대기 p95 60초 이내
- [ ] 만료·취소 파일 잔존 0건
- [ ] SSE 종료 후 연결·DB session 누수 없음
- [ ] CPU credit가 시험 동안 회복 불가능한 속도로 고갈되지 않음

모든 기준을 통과하기 전에는 안내용 동시 이용자 10명, 실행 중 review 1건을
확대하지 않는다.

## 9. 확장 판단

다음 중 하나가 반복되면 코드 미세 최적화보다 `t3.medium` 이상으로 상향한다.

- 메모리가 정상 부하에서 지속적으로 75%를 넘는다.
- swap 사용으로 p95 latency가 악화된다.
- CPU credit이 매일 고갈되거나 surplus 비용이 발생한다.
- review 대기 p95가 60초를 넘는다.
- 동시 검토 2건 이상이 제품 요구사항이 된다.

### 9.1 SSE 메모리 broadcaster 전환

초기 운영에서는 SQLite를 진행 상태의 원장으로 유지하고 SSE가 2~3초마다
상태를 조회한다. 다음 중 하나가 부하 시험 또는 운영 지표에서 반복되면 단일
API 프로세스 안에 review별 메모리 broadcaster를 추가한다.

- SSE 상한 20개 이하에서도 상태 조회가 일반 API의 p95 latency를 악화시킨다.
- SSE 상태 조회와 progress·TTL 쓰기가 겹칠 때 SQLite lock 또는 이벤트 루프
  지연이 발생한다.
- 2~3초보다 빠른 진행 이벤트 전달이 제품 요구사항이 된다.
- SSE 연결 상한을 20개보다 높여야 한다.

메모리 broadcaster는 DB를 대체하지 않고, DB commit 이후 SSE를 깨우는 알림
수단으로만 사용한다.

```text
MCP progress·terminal 상태 변경
  -> SQLite commit
  -> review_id 알림 발행
  -> SSE 구독자 깨우기
  -> DB snapshot과 sequence 재조회
  -> 클라이언트 전송
```

전환할 때 다음 조건을 함께 충족한다.

- [ ] 최초 연결과 재연결에서는 DB snapshot을 조회하고 `Last-Event-ID` 이후
      sequence만 전송한다.
- [ ] progress뿐 아니라 `COMPLETED`, `FAILED`, `CANCELLED`, `EXPIRED`의 DB
      commit 이후에도 알림을 발행한다.
- [ ] 조회와 대기 시작 사이에 발생한 알림을 놓치지 않도록 sequence를 다시
      확인하거나 `asyncio.Condition`에 동등한 원자적 대기 방식을 사용한다.
- [ ] 하나의 작업 큐를 여러 구독자가 소비하는 구조가 아니라 모든 SSE
      구독자를 깨우는 broadcast 구조를 사용한다.
- [ ] 알림 누락과 프로세스 재시작에도 최종 상태를 복구할 수 있도록 제한된
      주기의 DB 안전 조회를 유지한다.
- [ ] 연결 종료와 terminal 상태에서 review별 구독자와 메모리 객체를 정리한다.
- [ ] 동일 review 다중 구독, 알림 유실 경계, 재연결, 서버 재시작과 메모리 누수
      시험을 통과한다.

메모리 broadcaster는 단일 API 프로세스에서만 유효하다. API 프로세스를 둘
이상 실행하기 전에는 Redis Pub/Sub 등 프로세스 외부 전달 수단으로 교체하고,
DB snapshot을 통한 복구 원칙은 유지한다.

다중 인스턴스 확장은 다음 상태 전환 이후 진행한다.

1. SQLite를 PostgreSQL로 이전한다.
2. 사용자 파일을 암호화된 S3 임시 저장소로 이전한다.
3. 작업 상태와 실행 큐를 프로세스 밖으로 이동한다.
4. API와 MCP를 독립적으로 확장할 수 있게 분리한다.
5. API를 2개 이상 배치한 뒤 ALB를 도입한다.
