# 제한 큐 및 과부하 제어 구현 계획

> 상위 문서: [운영 검증 목록](운영%20검증%20목록.md)
>
> 범위: 운영 검증 목록 §3.1의 전체 계약 검토, Suggestions, 업로드에 대한
> 동시성·대기열·429·복구·취소 구현
>
> 배포 조건: 단일 EC2, API worker 1개, MCP worker 1개, SQLite

## 1. 목표

- 전체 계약 검토는 한 번에 1건만 실행한다.
- 전체 계약 검토는 실행 중인 1건과 별도로 최대 5건만 대기시킨다.
- SQLite의 `reviews.state=QUEUED`를 검토 작업의 영속 원장으로 사용한다.
- 요청마다 검토 실행용 `asyncio.Task`를 만들지 않는다.
- Suggestions는 1건만 실행하고 최대 5개의 HTTP 요청만 FIFO로 기다리게 한다.
- 업로드·범위 판별은 최대 2건만 동시에 실행하고 추가 요청은 기다리지 않고
  즉시 거부한다.
- 허용량을 넘으면 공통 오류 envelope, HTTP 429, `Retry-After`를 반환한다.
- 정상·비정상 재시작 후 작업을 중복 실행하거나 유실하지 않는다.
- QUEUED·REVIEWING 취소가 실행 슬롯과 대기 자리를 반환하도록 한다.

## 2. 범위 밖

- Redis, Celery, SQS 등 외부 메시지 큐 도입
- 여러 API 프로세스 또는 여러 EC2 사이의 분산 락
- SQLite에서 PostgreSQL로 이전
- RunPod 자체 worker 수와 GPU scheduler 변경
- 동시 검토 수를 2건 이상으로 확대
- reverse proxy의 접속·대역폭 제한

이 계획은 API worker가 반드시 1개라는 운영 조건에 의존한다. worker를 늘리면
인메모리 admission lock과 실행 큐가 프로세스마다 생기므로 이 설계를 그대로
사용할 수 없다.

## 3. 작업 유형별 제어 모델

| 작업 | 실행 | 대기 | 원장 | 초과 응답 |
| --- | ---: | ---: | --- | --- |
| 전체 계약 검토 | 1 | 5 | SQLite `reviews` | 429 |
| Suggestions | 1 | 5 | 현재 HTTP 요청 | 429 |
| 업로드·범위 판별 | 2 | 0 | 현재 HTTP 요청 | 429 |

전체 계약 검토만 접수 후 `202`를 반환하는 비동기 작업이다. 따라서 DB 복구가
필요하다. Suggestions와 업로드는 HTTP 요청이 완료될 때까지 결과를 기다리므로
재시작 시 클라이언트가 기존 멱등 키로 다시 요청하게 한다.

## 4. 전체 검토 scheduler 설계

### 4.1 구성 요소

`api/app/domains/reviews/scheduler.py`에 `ReviewScheduler`를 추가한다.

```text
ReviewScheduler
├─ admission_lock: 신규 접수·retry의 용량 판정을 직렬화
├─ pending: 최대 길이 5의 FIFO deque[review_id]
├─ pending_set: 중복 적재 방지
├─ condition: worker 깨우기
├─ worker_task: 앱 수명 동안 정확히 1개
├─ current_review_id: 현재 실행 중인 review
└─ current_execution_task: 현재 MCP 실행 Task 0~1개
```

`current_execution_task`는 취소 가능한 현재 검토 하나를 표현하기 위한 Task다.
요청마다 Task를 만들지 않으며 scheduler worker가 한 번에 하나만 생성하고
완료·취소될 때까지 기다린다.

### 4.2 DB와 메모리의 역할

- DB의 `QUEUED`가 접수 여부와 재시작 복구의 기준이다.
- `pending`은 실행할 ID를 빠르게 전달하는 최대 5칸의 런타임 mirror다.
- Review 본문이나 업로드 bytes를 큐에 넣지 않고 `review_id`만 저장한다.
- worker는 ID를 꺼낸 뒤 DB에서 최신 상태를 다시 읽는다.
- DB 상태가 더 이상 `QUEUED`가 아니면 실행하지 않고 다음 ID로 넘어간다.
- 메모리 큐와 DB가 불일치하면 DB를 기준으로 reconcile한다.

새로운 queue 테이블은 만들지 않는다. 기존 `reviews`의 상태, 생성 시각,
낙관적 잠금 version을 재사용한다.

### 4.3 Repository 확장

`SqlAlchemyReviewRepository`에 다음 조회를 추가한다.

- `count_queued() -> int`
- `list_queued(*, limit: int | None = None) -> list[Review]`
- `list_reviewing() -> list[Review]`

`list_queued()` 정렬은 `created_at ASC, id ASC`로 고정해 재시작 후에도 FIFO를
유지한다. 기존 `list_active()`는 호환을 위해 남기되 복구 코드에서는 QUEUED와
REVIEWING을 구분한다.

### 4.4 접수 원자성

신규 검토와 retry는 다음 순서로 처리한다.

```text
멱등 replay 조회
  ↓ replay 없음
ReviewScheduler.admission_lock 획득
  ↓
DB QUEUED 수와 pending 예약 수 확인
  ├─ 5 이상 → 429, DB 변경 없음
  └─ 여유 있음
       ↓
Review(QUEUED) + 멱등 응답 snapshot을 같은 트랜잭션에 저장
       ↓
DB commit
       ↓
pending에 review_id 추가 후 worker notify
       ↓
202 반환
```

다음 불변 조건을 지킨다.

- 같은 멱등 키의 성공 replay는 큐가 가득 찼어도 기존 202 응답을 재생한다.
- 429 응답은 성공 멱등 snapshot으로 저장하지 않는다.
- DB commit 전에 큐에 ID를 노출하지 않는다.
- commit 후 enqueue가 실패하면 요청을 성공으로 숨기지 않는다.
- commit과 enqueue 사이에 프로세스가 종료돼도 다음 시작의 DB reconcile이
  해당 QUEUED review를 다시 적재한다.

현재 `start_review`의 수동 멱등 처리와 `retry`의 `@idempotent` 처리 방식이
다르다. retry까지 위 admission lock을 commit 이후 enqueue까지 유지할 수
있도록 다음 중 하나로 통일한다.

1. 권장: 신규·retry 접수를 하나의 `ReviewAdmissionService`로 추출하고 두
   라우터가 같은 명시적 트랜잭션 흐름을 사용한다.
2. 대안: `@idempotent`에 admission context와 commit 이후 callback, 예외 시
   reservation 해제 hook을 추가한다.

공통 데코레이터에 review 전용 상태를 넣는 것보다 1안을 우선한다.

### 4.5 worker 실행

worker는 앱 시작 시 하나만 생성한다.

```text
pending에서 review_id 대기
  ↓
DB에서 Review 조회
  ├─ 없음 또는 QUEUED 아님 → skip
  └─ QUEUED
       ↓
current_review_id 설정
       ↓
execute_review Task 하나 생성·await
       ↓
성공·실패·취소 처리
       ↓
current 상태와 Task 참조 제거
       ↓
다음 pending 실행
```

`execute_review()`가 이미 DB에서 QUEUED를 재확인하고 REVIEWING으로 전환하므로
이 검증을 유지한다. 예상하지 못한 worker 예외 하나가 worker loop 전체를
종료시키지 않도록 review 단위로 예외를 격리하고 안전한 이벤트만 기록한다.

worker가 비정상 종료하면 readiness가 실패해야 한다. scheduler가 없는 상태에서
기존 방식으로 직접 Task를 만드는 fallback은 두지 않는다.

## 5. 앱 수명주기와 재시작 복구

### 5.1 시작 순서

현재 lifespan의 복구 순서를 다음처럼 바꾼다.

1. DB schema와 index 준비
2. 기존 `REVIEWING`만 `REVIEW_INTERRUPTED` retryable 실패로 전환
3. 기존 `QUEUED`는 실패시키지 않고 유지
4. 파일 cleanup 실행
5. MCP persistent session 연결
6. `ReviewScheduler` 생성
7. DB의 QUEUED를 FIFO로 reconcile
8. scheduler worker 1개 시작
9. readiness 활성화

현재 `_recover_interrupted_reviews()`는 QUEUED와 REVIEWING을 모두 실패시키므로
상태별 복구 함수로 교체한다.

정상 운영에서 재시작 시 QUEUED는 최대 5건이어야 한다. 기존 데이터나 버그로
5건을 초과하면 다음 정책을 적용한다.

- 오래된 5건은 FIFO로 복구한다.
- 초과분은 `REVIEW_QUEUE_RECOVERY_OVERFLOW`의 retryable 실패로 전환한다.
- 사용자에게 `RETRY_REVIEW`를 제공한다.
- 원문 파일은 재시도를 위해 TTL 정책에 따라 유지한다.
- 민감 본문 없이 초과 건수와 상태만 운영 이벤트로 기록한다.

### 5.2 종료 순서

1. scheduler의 신규 admission을 닫는다.
2. readiness를 실패로 전환한다.
3. 현재 실행 Task를 취소한다.
4. graceful shutdown이면 현재 REVIEWING을 `REVIEW_INTERRUPTED`로 확정한다.
5. pending의 DB 상태는 QUEUED로 유지한다.
6. worker와 cleanup task를 종료한다.
7. MCP session, DB, storage 순으로 닫는다.

강제 종료로 4단계를 수행하지 못해도 다음 시작에서 REVIEWING 복구가 처리한다.

## 6. 취소 처리

### 6.1 QUEUED 취소

1. DB Review를 `CANCELLED`로 저장하고 commit한다.
2. scheduler의 `pending`에서 해당 ID를 제거한다.
3. condition을 깨워 다음 작업과 신규 admission이 진행되게 한다.
4. 기존 취소 정책에 따라 원본 파일과 결과를 정리한다.

임의 위치 삭제가 필요하므로 제거할 수 없는 일반 `asyncio.Queue` 대신 최대
5칸의 `deque + asyncio.Condition`을 사용한다.

DB commit과 메모리 제거 사이에 worker가 ID를 가져가더라도 worker 또는
`execute_review()`가 최신 DB 상태를 확인하므로 CANCELLED 작업은 실행되지
않는다.

### 6.2 REVIEWING 취소

1. `current_review_id`가 일치하면 `current_execution_task.cancel()`을 호출한다.
2. Task 종료를 기다린다.
3. DB Review를 `CANCELLED`로 저장한다.
4. current slot을 비우고 worker가 다음 QUEUED를 실행하도록 깨운다.

완료와 취소가 경합하면 기존 낙관적 잠금과 terminal 상태 재조회로 최종 상태를
한 번만 확정한다. 이미 COMPLETED가 된 뒤의 삭제형 취소라는 현재 API 계약도
유지한다.

## 7. Suggestions 제한

`api/app/core/admission.py`에 취소 가능한 `BoundedFifoGate`를 추가한다.

설정값:

- 실행 동시성: 1
- 최대 대기 요청: 5
- queue wait timeout: 초기 60초

동작:

```text
Suggestions 멱등 replay 조회
  ↓ replay 없음
실행 슬롯 확인
  ├─ 비어 있음 → 즉시 실행
  ├─ 실행 중 + 대기 < 5 → FIFO 대기
  └─ 실행 중 + 대기 = 5 → 429
```

gate는 `generate_suggestion()` 전체를 감싼다. 이 함수에는 grounding MCP 호출과
실제 Qwen 호출이 모두 있으므로 둘을 함께 제한해야 공유 MCP session에 동시
grounding 요청이 쌓이지 않는다.

- 클라이언트 연결 취소와 queue wait timeout은 대기자 수를 즉시 줄인다.
- 실행 함수의 성공, 오류, timeout, cancellation 모두 `finally`에서 슬롯을
  반환한다.
- 대기 순서는 FIFO로 유지한다.
- 프로세스가 재시작되면 HTTP 연결은 실패하고 클라이언트는 같은 멱등 키로
  재시도한다.
- replay는 gate에 들어가지 않으므로 큐가 가득 차도 기존 결과를 반환한다.

## 8. 업로드 제한

업로드는 대기열 없이 `ImmediateConcurrencyLimiter(limit=2)`를 사용한다.

limiter 범위:

1. `UploadFile.read`
2. 형식·암호화·손상 검증
3. 임시 파일 저장
4. MCP `assess_contract_scope`
5. 세션 DB 저장 또는 실패 정리

세 번째 동시 요청은 기다리지 않고 즉시 429를 반환한다. 성공·검증 오류·MCP
timeout·클라이언트 취소 모두 `finally`에서 슬롯을 반환한다.

FastAPI가 route에 진입하기 전에 multipart를 임시 저장할 수 있으므로 이
limiter만으로 네트워크 body 수신을 제한할 수는 없다. reverse proxy의
`client_max_body_size`, request buffering, 연결 제한은 별도 배포 항목으로
유지한다.

## 9. 설정

`Settings`와 운영 env에 다음 값을 추가한다.

```dotenv
REVIEW_WORKER_COUNT=1
REVIEW_QUEUE_CAPACITY=5
REVIEW_QUEUE_RETRY_AFTER_SECONDS=30

SUGGESTION_CONCURRENCY_LIMIT=1
SUGGESTION_QUEUE_CAPACITY=5
SUGGESTION_QUEUE_WAIT_SECONDS=60
SUGGESTION_RETRY_AFTER_SECONDS=20

UPLOAD_CONCURRENCY_LIMIT=2
UPLOAD_RETRY_AFTER_SECONDS=5
```

- 모든 값은 양수로 검증한다.
- 현재 배포에서는 `REVIEW_WORKER_COUNT`를 1 이외로 설정하면 시작을 거부한다.
- 설정 기본값, 환경 파일, `.env.example`, 설정 테스트를 함께 변경한다.
- queue capacity를 런타임에 변경하지 않고 재시작을 통해 적용한다.

## 10. 429 오류 계약

공통 오류에 `OverCapacityError`를 추가하고 HTTP 429에 매핑한다.

| 작업 | 오류 코드 | Retry-After |
| --- | --- | ---: |
| 검토 | `REVIEW_QUEUE_FULL` | 30초 |
| Suggestions | `SUGGESTION_QUEUE_FULL` | 20초 |
| 업로드 | `UPLOAD_CAPACITY_EXCEEDED` | 5초 |

공통 응답 예:

```json
{
  "error": {
    "code": "REVIEW_QUEUE_FULL",
    "message": "현재 검토 요청이 많습니다. 잠시 후 다시 시도해 주세요.",
    "field": null,
    "retryable": true,
    "next_action": "RETRY_LATER",
    "details": {}
  },
  "meta": {
    "request_id": "...",
    "timestamp": "..."
  }
}
```

응답에는 다음 헤더를 포함한다.

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 30
X-Request-ID: ...
Cache-Control: no-store
```

큐에 있는 다른 사용자의 수, session ID, review ID는 오류 details에 노출하지
않는다. `COMMON_ERROR_RESPONSES`, 업로드 응답, Suggestions·review OpenAPI에
429를 문서화한다.

fallback하지 않고 테스트 fixture가 작은 runtime을 제공하게 한다.

## 12. 구현 순서

### 단계 1. 설정과 오류 계약

- Settings와 환경 파일에 제한값을 추가한다.
- `OverCapacityError`와 429 handler를 구현한다.
- `Retry-After`, `Cache-Control: no-store`, 요청 ID를 검증한다.
- OpenAPI 공통 오류를 갱신한다.

완료 조건: 세 오류 코드가 동일한 envelope와 올바른 헤더로 반환된다.

### 단계 2. 공통 gate

- `BoundedFifoGate`와 `ImmediateConcurrencyLimiter`를 구현한다.
- FIFO, 최대 대기자, timeout, cancellation, 예외 시 release를 단위 테스트한다.

완료 조건: 실행 또는 대기 수가 설정 상한을 넘지 않고 취소 후 즉시 재사용된다.

### 단계 3. review scheduler

- Repository의 상태별 조회를 추가한다.
- 최대 5칸 pending deque와 단일 worker를 구현한다.
- `execute_review`를 scheduler에서만 호출하게 한다.
- 직접 `_schedule_review()`와 `app.state.review_tasks`를 제거한다.

완료 조건: 여러 접수에도 MCP 검토 호출은 동시에 1개만 존재한다.

### 단계 4. 접수·멱등성 통합

- 신규와 retry를 `ReviewAdmissionService`로 통합한다.
- replay → capacity → DB commit → enqueue 순서를 적용한다.
- 429를 멱등 성공 snapshot으로 저장하지 않는다.

완료 조건: 큐가 가득 찬 상태에서도 기존 멱등 키는 같은 202를 재생하고 새 키만
429를 받는다.

### 단계 5. 복구와 종료

- REVIEWING만 interrupted 실패로 복구한다.
- QUEUED를 FIFO로 scheduler에 복원한다.
- graceful shutdown과 overflow 복구 정책을 구현한다.
- readiness에 scheduler 상태를 포함한다.

완료 조건: 재시작 전 QUEUED는 한 번만 실행되고 REVIEWING은 자동 재실행되지
않으며 retryable 실패가 된다.

### 단계 6. 취소

- pending 임의 제거와 current Task 취소를 연결한다.
- QUEUED·REVIEWING·완료 직전 경합을 테스트한다.

완료 조건: 취소 응답이 끝났을 때 해당 작업이 실행·대기 용량을 점유하지 않는다.

### 단계 7. Suggestions와 업로드

- Suggestions 전체 use case에 FIFO gate를 적용한다.
- 업로드 전체 use case에 즉시 limiter를 적용한다.
- 멱등 replay와 timeout·취소 release를 검증한다.

완료 조건: Suggestions는 1+5, 업로드는 2를 절대 넘지 않는다.

### 단계 8. 회귀·문서·관측

- OpenAPI를 재생성한다.
- 전체 API 테스트, lint, type 검사 범위를 실행한다.
- queue depth, active 작업, 거부 수, queue wait 로그·메트릭을 연결한다.
- 운영 검증 목록의 구현 항목을 결과에 따라 갱신한다.

완료 조건: 전체 회귀 통과와 운영 부하 시험 진입 조건 충족.

## 13. 테스트 계획

### 13.1 단위 테스트

- pending FIFO와 중복 review ID 방지
- pending 5건에서 여섯 번째 enqueue 거부
- worker 실행 동시성 최대 1
- QUEUED 취소 후 같은 순간 새 작업 접수 가능
- REVIEWING 취소 후 다음 작업 실행
- 실행 성공·실패·timeout·cancellation 후 슬롯 반환
- Suggestions active 1 + waiting 5 유지
- Suggestions 일곱 번째 요청 429
- Suggestions 대기 취소와 timeout 후 자리 반환
- 업로드 두 건 실행 중 세 번째 요청 429
- Retry-After 값과 오류 envelope

### 13.2 API 통합 테스트

- 서로 다른 7개 세션에서 검토를 동시에 접수한다.
  - 1건 실행
  - 5건 QUEUED
  - 1건 `429 REVIEW_QUEUE_FULL`
- 큐가 가득 찬 상태에서 같은 멱등 키 replay는 202와 같은 review ID를 반환한다.
- 큐가 가득 찬 상태에서 새 멱등 키는 성공 snapshot을 만들지 않는다.
- QUEUED 하나를 취소한 직후 새 검토 하나가 202로 접수된다.
- REVIEWING을 취소하면 FIFO 다음 검토가 시작된다.
- retry 접수도 신규 접수와 같은 5칸을 공유한다.
- Suggestions 7개 동시 요청에서 1개 실행, 5개 대기, 1개 429를 확인한다.
- 업로드 3개 동시 요청에서 2개 실행, 1개 429를 확인한다.

### 13.3 재시작 테스트

- DB에 QUEUED 5건과 REVIEWING 1건을 준비한다.
- 시작 후 REVIEWING은 `REVIEW_INTERRUPTED`가 된다.
- QUEUED 5건은 FIFO로 한 번씩 실행된다.
- commit 후 메모리 enqueue 전 종료를 모사해 DB reconcile로 복구한다.
- QUEUED 6건의 legacy 상태에서 초과 1건이 retryable overflow 실패가 된다.
- shutdown 중 현재 작업만 interrupted되고 pending은 QUEUED로 남는다.

### 13.4 회귀 테스트

- 세션당 active review 1건 제약
- 신규·retry 멱등성 경합
- SSE sequence와 terminal 이벤트
- 취소 시 파일 삭제
- TTL 만료 유예와 완료 후 재개
- MCP timeout·invalid response
- Suggestions structured output repair 최대 1회
- API OpenAPI snapshot 동기화

## 14. 관측 항목

민감 입력 없이 다음 이벤트·메트릭을 기록한다.

- review queue depth
- review active 0/1
- review queue wait milliseconds
- suggestion active·waiting
- suggestion queue wait milliseconds
- upload active 0~2
- 작업 유형별 429 누계
- worker loop alive
- startup recovered QUEUED·REVIEWING·overflow 건수

review ID는 기존 비식별 운영 정책 범위에서만 사용하고 session token, 계약서
본문, prompt, 결과 본문은 기록하지 않는다.
