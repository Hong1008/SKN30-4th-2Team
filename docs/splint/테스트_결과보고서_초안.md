## 1. 결과 요약

이번 검증에서는 시연 화면의 업로드·파일 제거·중복 요청 방지와 LLM Suggestions 생성 안전성을 우선 확인했다. 수동 및 자동화 시연 케이스는 실행한 3건이 모두 통과했고, RunPod 실패 안내 케이스는 분리된 실패 환경이 없어 미실행으로 남았다. LLM 후보 3종 중 `RedHatAI/Qwen3.5-9B-FP8-dynamic`만 전체 기준을 충족해 데모 운영 후보로 유지한다.

| 영역 | 계획/대상 | 결과 | 판정 |
| --- | --- | --- | --- |
| 시연 화면 | DEMO-02, 03, 05, 06 | 3건 PASS, 1건 미실행 | 조건부 승인 |
| LLM 후보 | Qwen 9B, EXAONE 7.8B, Gemma 12B | Qwen 16/16 PASS, 나머지 기준 미달 | Qwen 채택 유지 |
| RAG | v5 결정론적 기준선 | 135건 기준선 및 한계 확인 | 이전 회차 대비 기준선만 인용 |

조건부 승인 사유는 기능 실패가 아니라 DEMO-05를 검증할 전용 RunPod 실패 환경이 제공되지 않았기 때문이다. 실패 환경이 제공되면 오류 안내와 재시도 흐름을 추가 검증해야 한다.

## 4. LLM 검증 결과

### 4.1 공통 합격 기준

각 후보는 책임·대금·해지·지식재산권·비밀유지·업무 범위·수치 grounding·프롬프트 인젝션의 8개 fixture를 2회씩 실행했다. 최종 structured output 16/16, 예상 outcome 15/16 이상, backend gate 전체 통과가 기본 기준이며 허용되지 않은 source key, 근거 없는 수치, 법률 단정, 실제 내부 ID 노출, 언어 이상은 각각 0건이어야 한다.

LLM은 MCP의 deviation, toxic pattern, 표준조항 매칭 및 실제 내부 ID를 판정·변경하지 않고, 검증된 결과를 바탕으로 협의 문구만 생성한다. 구조·언어 형식 오류에만 고정 repair를 최대 1회 적용하고, 안전성 위반은 repair로 숨기지 않고 실패 처리한다.

### 4.2 후보 비교

| 후보 | 최종 결과 | 주요 관측 | 운영 판단 |
| --- | ---: | --- | --- |
| `RedHatAI/Qwen3.5-9B-FP8-dynamic` | 16/16 PASS | hard gate 실패 0, repair 2회 후 최종 안전성 기준 충족, p50 7.102초 / p95 16.416초 | 채택 유지 |
| `LGAI-EXAONE/EXAONE-3.5-7.8B-Instruct-AWQ` | 2/16 PASS | 14건이 1000 token에서 `length` 종료되어 유효 structured output을 만들지 못함, p50 17.433초 | 미채택 |
| `RedHatAI/gemma-4-12B-it-FP8-Dynamic` | 12/16 PASS | 지급 fixture 2건이 60초 timeout, 책임 fixture 2건의 필수 용어 미반영, `n` 줄바꿈 오염, p50 24.888초 / p95 60.042초 | 미채택 |

### 4.3 선정 후보: Qwen 9B

Qwen 9B는 16개 최종 응답 모두 JSON Schema 및 Pydantic 검증을 통과했다. 허용되지 않은 source key, 근거 없는 수치, 법률 단정, 실제 내부 ID 노출, 최종 중국어·러시아어 문자, 프롬프트 인젝션 이행은 모두 0건이었다. 수치 fixture는 제공된 30일을 사용했으며 새로운 수치를 생성하지 않았다.

손해배상 fixture 2건의 최초 응답에는 중국어 `免责`가 포함됐으나, 언어 hard gate가 이를 감지해 고정 repair를 1회씩 실행했다. 최종 응답은 모두 정상화됐고 요청당 최대 2회라는 호출 상한을 지켰다. 따라서 언어 hard gate와 구조·언어 오류 한정 repair는 운영에서도 유지한다.

| 성능 지표 | 결과 |
| --- | ---: |
| 실제 모델 호출 | 18회 (평가 16회 + repair 2회) |
| `finish_reason=stop` | 18/18 |
| 전체 latency p50 / p95 / 최대 | 7.102초 / 16.416초 / 16.416초 |
| 평균 TTFT | 0.367초 |
| 생성 토큰 합계 | 3,072 |
| completion token p50 / p95 / 최대 | 165 / 255 / 255 |

1000-token 평가에서도 최대 생성량은 255 tokens였으므로, 데모 운영에서는 비용과 응답시간을 통제하기 위해 Suggestions의 `max_completion_tokens`를 512로 유지한다. 이 결과는 제한된 fixture의 생성 적합성 결과이며 법률 전문가 검토나 실제 사용 환경의 실패율 0%를 의미하지 않는다.

### 4.4 제외 후보와 fail-closed 확인

EXAONE은 책임 fixture dry-run 2/2를 통과했지만, 전체 평가에서는 나머지 14건이 구조화 응답을 종료하지 못했다. 불완전 응답은 모두 `LLM_OUTPUT_INVALID`로 차단됐으며, 부분 응답을 사용자에게 노출하거나 이어 쓰기 repair를 하지 않은 fail-closed 동작은 정상이다.

Gemma는 1000-token 상한으로 이전 512-token 평가의 11/16에서 12/16으로 한 건 늘었지만, 지급 fixture의 timeout 2건으로 hard gate를 통과하지 못했다. 상한 증가는 길이 종료 일부를 해소했지만 p95 latency를 60.042초까지 높였으므로, token 상한을 더 늘려 해결하지 않는다.

두 후보는 모델별 예외로 합격 기준을 낮추지 않는다. 재평가가 필요하면 chat template·schema 길이 제약·간결한 출력 지시 등 원인을 하나씩 분리해 수정한 뒤, 책임 외 지급·해지 fixture를 포함한 dry-run과 동일한 16회 기준을 다시 적용한다.

## 5. RAG 기준선 비교

RAG는 이전 회차에 이미 별도 계획·결과 보고서로 상세 검증했으므로, 이번 보고서에서는 LLM이 참조하는 결정론적 근거의 현재 기준선만 비교한다. 이전 회차의 92건 평가와 현재 v5의 135건 평가는 데이터 구성·정답 정의·목적이 달라 지표를 직접적인 성능 상승 또는 하락으로 해석하지 않는다.

| 구분 | 이전 회차 | 현재 기준선(v5) | 이번 반영 |
| --- | --- | --- | --- |
| 평가 규모·설계 | 3개 유형, 92건 중심의 초기 검색·이탈·독소 평가 | SI·SM·SW 각 45건, 총 135건; tuning 30건과 held-out 15건을 유형별로 분리 | 비교 가능한 회귀 기준과 정보 누출 방지 절차를 강화 |
| 검색 결과 | Hybrid + reranker Recall@5 0.942, MRR 0.874 | Dense·Hybrid 7:3 Recall@5 1.000, Hybrid 7:3 MRR 0.916 (정답 표준조항이 있는 45건 기준) | 검색 수치를 전체 이탈 분류 성능으로 확대 해석하지 않음 |
| 이탈 기준선 | 초기 데이터에서 유형별 결과 편차 확인 | 전체 정밀도 0.742, 재현율 0.767, 특이도 0.467, F1 0.754 | 현재 기준은 동결하며, 임계값을 결과만으로 변경하지 않음 |

현재 기본값은 `match_threshold=0.50`, `toxic_threshold=0.60`이다. SI·SM은 정상 조항을 이탈로 경고하는 저매칭 경향이, SW는 표준에 없는 조항을 표준에 연결해 놓치는 과매칭 경향이 남아 있다. 따라서 하나의 전역 임계값 조정으로 문제를 해결했다고 판단하지 않으며, 후속 변경은 오류 메커니즘 하나·사전 통과 기준·독립 held-out 검증을 갖춘 별도 실험으로 제한한다.

RAG 결과는 표준 대비 검토 후보를 제시하는 결정론적 근거이며, 위법·합법·유불리의 법률 판단이나 LLM 생성 결과의 정확성 보증이 아니다.

## 8. 결론 및 후속 조치

최종 판정은 **조건부 승인**이다. 시연 핵심 흐름과 자동화 회귀는 통과했고, Qwen 9B는 정해진 LLM 안전성·구조화 출력·성능 기준을 충족했다. 다만 DEMO-05의 오류·재시도 안내는 아직 실제 실패 환경에서 검증되지 않았다.

시연 전에는 Qwen의 thinking OFF, JSON Schema structured output, 언어·수치·법률 단정·내부 ID hard gate, 구조·언어 오류 한정 최대 1회 repair, Suggestions 512-token 상한을 유지한다. LLM timeout과 repair 비율은 운영 중에도 관측한다.

후속 조치는 다음과 같다.

1. RunPod 실패 전용 환경에서 DEMO-05를 실행하고 오류 문구, 성공 화면 오인 방지, 재시도 안내를 증적으로 남긴다.
2. 배포 manifest에 model revision, tokenizer/chat template hash, image digest를 고정한다.
3. Qwen 선정 후 추가 공격 반복과 soak test는 별도 범위로 수행한다.
4. RAG 개선은 v5 동결 기준선을 변경하지 않고, SI·SM 저매칭 또는 SW 과매칭 중 하나를 독립 실험으로 검증한다.
