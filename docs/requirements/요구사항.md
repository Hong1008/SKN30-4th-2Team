# WorkShield 확정 사용자 요구사항 요약

> 본 문서는 사용자 관점의 확정 요구사항 요약본이다. SSE·polling, API 필드, LLM provider, MCP 호출 구조 등 구현 방식은 이 문서의 확정 범위가 아니며 별도 기술 문서에서 관리한다.

## 1. 계약서 업로드 및 유형 확인

- HWP, HWPX, PDF, DOCX 계약서를 업로드할 수 있어야 한다.
- 손상·암호화·빈 문서·지원하지 않는 형식·허용 크기 초과 파일은 검토 전에 차단하고 안내해야 한다.
- 시스템은 SW 프리랜서 용역, SI 하도급, SM 하도급 유형을 분석해 제시해야 한다.
- 사용자는 계약 유형을 직접 선택하거나 변경할 수 있어야 한다.
- 계약 유형이 불확실하거나 범위 밖이면 사용자 확인 전 검토를 진행하지 않아야 한다.

## 2. 검토 진행 상황

- 사용자는 검토 단계와 현재 진행 상태를 확인할 수 있어야 한다.
- 진행 상태는 실제 서버 검토 상태를 반영해야 하며, 프론트가 임의로 완료를 표시해서는 안 된다.
- 검토 완료·실패·취소 시 사용자가 다음 행동을 알 수 있어야 한다.

## 3. 검토 결과

- 사용자 조항, 대응 표준 조항, 비교 근거, 검토 상태를 조항별로 확인할 수 있어야 한다.
- `NONE`, `EXTRA`, `NO_MATCH`, `MISSING` 상태를 구분해 표시해야 한다.
- 상태·카테고리·키워드로 결과를 탐색할 수 있어야 한다.
- 결과를 위법·합법·승소 등 법적 결론으로 단정해서는 안 된다.
- 불공정 패턴과 대응 표준 조항이 없는 항목을 별도로 확인할 수 있어야 한다.

## 4. 법령 근거

- 법령 근거가 확인된 결과에는 관련 법령 정보를 표시해야 한다.
- 법령 근거가 없거나 조회에 실패한 경우 법령을 임의로 생성하지 않고 해당 상태를 안내해야 한다.
- 법령 원문과 시스템의 설명은 구분해서 표시해야 한다.

## 5. AI 챗봇

- 현재 계약서·검토 결과·연결된 법령 자료에 한정해 답변해야 한다.
- 실질적인 답변에는 근거 출처를 표시해야 한다.
- 범위 밖 질문, 근거가 부족한 질문, 법령 조회 실패 상황에서는 추측 답변을 하지 않고 제한 또는 실패 상태를 안내해야 한다.
- 환각과 프롬프트 인젝션을 방지해야 한다.
- 새 검토, 검토 폐기, 세션 만료 또는 검토 대상 변경 시 이전 챗봇 대화가 남지 않아야 한다.

## 6. 수정·협의 문구

- 사용자 조항과 대응 표준 조항을 근거로 참고용 대안 문구를 제공해야 한다.
- 미확정 금액·기간·조건은 임의 생성하지 않고 `[확인 필요]`로 표시해야 한다.
- 제안 문구는 복사할 수 있어야 하며 원본 계약서에 자동 반영해서는 안 된다.
- 충분한 근거가 없으면 일반적인 문구를 임의로 생성하지 않아야 한다.

## 7. 세션 및 보안

- 사용자는 자신의 검토 세션에만 접근할 수 있어야 한다.
- 계약서와 대화 이력은 영구 저장하지 않고 세션 만료 후 정리해야 한다.
- 전송 구간을 보호하고 API 키·접속정보·계약서 원문·대화 본문을 운영 로그에 남기지 않아야 한다.
