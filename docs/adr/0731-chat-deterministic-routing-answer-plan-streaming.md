# 계약 검토 챗봇의 결정적 라우팅, 답변 계획과 스트리밍

- 상태: Accepted
- 결정일: 2026-07-31
- 대체 범위:
  - [0730 LangGraph 기반 질문 분류와 근거 제한 채팅](0730-langgraph-chat-prompt-routing.md)의 Chat 처리 구조 전체
  - [0728 Chat·Suggestions 단계별 근거 사용과 법령 조회 fallback](0728-chat-grounding-fallback.md)의 Chat 관련 결정
- 유지 범위:

  - 운영 답변 모델과 provider는 [0728 운영 LLM을 RunPod vLLM으로 전환](0728-vllm-production-provider.md)을 따름

## 1. 맥락

계약 검토 챗봇은 특정 조항 설명뿐 아니라 상태의 의미, 상태별 전체 목록,
표준조항 비교, 주의 신호, 법령 참고자료와 이전 답변을 가리키는 후속 질문을
함께 처리해야 한다. 실제 사용 과정에서 다음 문제가 반복됐다.

- 전체 검토 질문에서도 앞쪽 제1조~제3조만 답변하는 경향
- `EXTRA`와 `toxic_patterns`를 같은 의미로 해석해 제공되지 않은 위험 이유 생성
- `제1조`는 인식하지만 `조항 1`은 인식하지 못해 서비스 정책 답변으로 잘못 전환
- 이전 질문의 대상을 잃어 “각 조항”, “그중”, “불이익은?”을 근거 부족으로 처리
- 법령 원문이 조회되지 않으면 사용자 조항과 표준조항이 있어도 전체 답변 거절
- 긴 목록을 한 번에 생성해 출력 상한에서 답변이 중단되거나 일부 항목만 설명
- 모델이 `[상태:]`, `[카테고리:]` 같은 내부 표현을 본문에 반복
- 스트리밍 진행 상태와 답변 말풍선의 위치가 바뀌고 완료 전 복사 등 동작이 노출

기존 0730 ADR은 LangGraph, 2,400자 문맥 절단, 최근 대화 원문과 법령 질문
전용 grounding을 전제로 했다. 현행 코드는 결정적 선처리, 의미 상태 토큰,
`AnswerPlan`, 분할 SSE를 사용하므로 새로운 기준 문서가 필요하다.

## 2. 결정

### 2.1 처리 파이프라인

Chat은 LangGraph가 아니라 다음 순서의 애플리케이션 서비스 파이프라인으로
처리한다.

1. 완료된 Review와 UI의 `focus_clause_id`를 검증한다.
2. 서버가 확정할 수 있는 신호 귀속, 신호 검색, 상태 의미·목록·우선순위와
   서비스 정책 질문을 결정적으로 처리한다.
3. 남은 질문은 이어보기 상태, 의미 기반 후속 문맥, 명시적 비교 의도, 외부
   질문 분류기 순서로 질문 유형을 선택한다.
4. 질문 유형과 대상 결과군으로 `AnswerPlan`을 만든다.
5. 필요한 경우에만 MCP 법령 원문을 계획에 추가한다.
6. 계획을 항목·토큰 예산에 따라 나누고 Qwen 답변 모델을 순차 호출한다.
7. 생성 결과를 정규화하고 출처·제한·질문 유형을 모델 본문과 분리해 반환한다.

결정적 선처리는 LLM이 필요 없는 질문의 지연과 변동성을 줄이는 역할을 한다.
정규식과 키워드는 조문 번호, 공개 상태 용어와 제한된 고정 의도에만 사용한다.
나머지 자유 표현은 구조화 출력 질문 분류기가 처리한다.

### 2.2 공개 질문 유형

분류 결과는 아래 코드 중 하나이며 프런트는 `/metadata`의
`chat_question_category_details`에서 표시 라벨을 얻는다.

| 코드 | 용도 |
| --- | --- |
| `CONTRACT_CONTENT` | 특정 사용자 조항·표준조항의 내용과 영향 질문 |
| `REVIEW_ANALYSIS` | 전체 검토 결과와 여러 조항 분석 |
| `REVIEW_STATUS_DEFINITION` | 검토 상태의 공개 의미 |
| `REVIEW_RESULT_LIST` | 특정 상태 조항의 전체 목록과 개수 |
| `REVIEW_CLAUSE_COMPARISON` | 대상 조항과 표준조항 후보의 항목별 비교 |
| `REVIEW_PRIORITY` | 긴급도·수정 우선순위 정보의 존재 여부 |
| `SIGNAL_SEARCH` | 특정 주의 문구 유사 신호와 연결된 조항 검색 |
| `LEGAL_REFERENCE` | 법령명·조문·원문 참고자료 요청 |
| `SERVICE_POLICY` | 표준조항, 상태와 주의 신호의 서비스 운영 기준 |
| `OUT_OF_SCOPE` | 계약 검토 자료의 범위를 벗어난 질문 |

질문 유형은 근거 선택을 위한 코드이며 일반적인 답변 거절 조건으로 사용하지
않는다. `OUT_OF_SCOPE`만 모델과 MCP 호출 전에 종료한다. 선택 결과 데이터가
실제로 비었을 때만 `INSUFFICIENT_GROUNDING`을 반환한다.

### 2.3 대상 선택과 검토 결과 경계

답변 대상은 다음 우선순위로 선택한다.

1. UI가 전달한 `focus_clause_id`
2. 현재 질문에 명시된 조문 번호
3. `EXTRA`, `NO_MATCH`, `MISSING`처럼 질문에 명시된 결과군
4. 검증된 `conversation_token`이 가리키는 직전 대상
5. 전체 Review 결과

명시적 대상은 이전 대화 대상을 대체한다. 조문 표기는 `제1조`, `1조`,
`제 1 조`, `조항 1`을 같은 번호로 정규화한다. 일치하지 않는 조항을 앞쪽
조항으로 대체하지 않는다.

`clause_results`의 `NONE`·`EXTRA`·`NO_MATCH` 사용자 조항과
`missing_standard_clauses`의 `MISSING` 표준조항 후보는 계획·출처·화면에서
계속 분리한다. 조항과 목록은 Review의 원래 순서를 유지한다.

### 2.4 후속 대화 문맥

서버는 답변 원문을 장기 문맥으로 저장하지 않는다. 완료 응답마다 예측 불가능한
`conversation_token`을 발급하고 다음 의미 상태만 보관한다.

- 직전 질문 유형
- 단일 조항 또는 결과군 등 대상 종류
- 선택한 사용자 조항 ID 목록
- 결과 상태 코드 목록
- `MISSING` 표준조항 ID 목록
- 분할 답변의 다음 오프셋

“각 조항”, “그중”, “위 목록”, “불이익은?”과 같은 후속 질문은 이 상태로
대상을 복원한다. 답변 프롬프트에는 이전 대화 원문을 넣지 않으며 현재 질문만
답하도록 명시한다. 호환용 `history` 필드는 유지하지만 답변 근거로 사용하지
않는다.

### 2.5 상태·주의 신호와 법령 grounding

검토 상태와 주의 신호는 다음 경계를 유지한다.

- `NONE`, `EXTRA`, `NO_MATCH`, `MISSING`의 라벨과 설명은 기존
  `RESULT_CODE_LABELS`, `RESULT_CODE_DESCRIPTIONS` 및 `/metadata`를 사용한다.
- `toxic_patterns`는 표준 대비 상태와 독립적인 알려진 주의 문구 유사 신호다.
- 주의 신호 코드는 검토 시점에 저장한 MCP title 또는 metadata label로만
  표시한다. 라벨이 없으면 내부 코드를 노출하지 않고 Pydantic 필드의 일반
  설명을 사용한다.
- MCP가 제공하지 않은 탐지 이유, 불공정성, 분쟁 가능성과 법적 결론은 만들지
  않는다.

신호 질문은 대상을 구분한다.

- “제 계약서의 주의 신호”는 신호가 연결된 모든 사용자 조항을 라벨과 함께
  나열한다.
- “조항 1의 주의 신호”는 제1조만 조회한다.
- 대상 조항에 기록된 신호가 없으면 그 사실을 알리되 안전·적법 판단으로
  확장하지 않는다.
- 대상이 없는 “주의 신호가 무엇인가요?”만 `SERVICE_POLICY`로 설명한다.

단순 신호 식별은 법령 MCP를 호출하지 않는다. 신호가 기록된 선택 조항에 대해
문제·불이익·위험·영향·효과·확인 사항을 묻는 경우에는 해당 표준조항
`category`로 `get_category_grounding`을 호출한다.

법령 질문과 신호 영향 질문은 사용자 조항과 표준조항 후보를 기본 근거로
유지한다. grounding이 `OK`이면 법령명·조문·원문을 `LAW` 출처와 함께 추가한다.
조회 결과가 없거나 실패하면 조항 설명은 계속하고 연결된 법령 참고자료를 현재
검토 결과에서 확인하지 못했다는 고정 안내를 붙인다. 다만 특정 법령명·법조문
원문 자체를 직접 요구했는데 원문이 없으면 추측하지 않고 근거 부족으로 종료한다.

### 2.6 답변 계획, 토큰 예산과 분할 생성

LLM 호출 전 서버가 `AnswerPlan`을 만든다. 각 항목은 사용자 조항 또는
`MISSING` 표준조항, 원문, 검토 상태, 대응 표준조항, 공개 주의 신호 라벨과
검증된 출처를 포함한다.

- 답변 모델 호출당 `max_completion_tokens=512`, temperature `0`, seed `42`,
  thinking OFF를 유지한다.
- vLLM의 `--max-model-len 8128`에서 출력 512토큰과 템플릿 여유 512토큰을
  제외해 prompt 상한을 7,104토큰으로 둔다.
- 한 묶음은 최대 3개 항목이며 vLLM `/tokenize` 결과가 상한을 넘으면 다음
  묶음으로 이동한다.
- 운영 tokenizer를 사용할 수 없으면 문자 수를 보수적 상한으로 사용한다.
- 단일 항목도 상한을 넘으면 문단, 이후 3,000자 조각으로 나누되 원문을 조용히
  버리지 않는다.
- 운영 vLLM 동시성 기준이 1이므로 답변 묶음은 병렬이 아니라 순차 생성한다.

모델은 현재 묶음만 Markdown `##` 섹션으로 답하고 공통 서론, 면책과 앞 묶음을
반복하지 않는다. 서버는 묶음을 순서대로 결합하고 출처를 중복 제거한다.

### 2.7 SSE와 부분 실패

스트림은 다음 공개 이벤트를 사용한다.

| 이벤트 | 의미 |
| --- | --- |
| `progress` | 내부 추론이 아닌 서버 작업 단계와 묶음 번호 |
| `delta` | 누적 표시할 답변 본문 조각 |
| `segment_complete` | 완료 묶음 번호와 검증된 출처 |
| `completed` | 최종 `ChatResponse`와 선택적 continuation |
| `failed` | 안전한 오류, 부분 답변 존재 여부와 재개 오프셋 |

중간 묶음이 실패해도 이미 전달한 답변과 출처를 보존한다. continuation은 다음
항목 오프셋과 남은 묶음 수를 제공하고, 같은 대화 토큰의 “이어서 답변” 요청은
남은 항목만 생성한다.

### 2.8 본문·메타데이터와 프런트 표시

모델은 `[상태:]`, `[카테고리:]`, `[답변:]`을 생성하지 않으며 서버는 남아 있는
레거시 헤더를 정규화 단계에서 제거한다. 질문 유형, 제한 사유, 출처와 면책은
모델 본문이 아니라 응답 필드로 전달한다. 프런트는 코드 자체 대신 `/metadata`의
라벨을 표시한다.

답변 본문은 GitHub Flavored Markdown으로 렌더링하되 raw HTML은 허용하지
않고 HTTP(S) 링크만 새 창으로 연다. 생성 중 assistant placeholder는 사용자
질문 바로 다음에 생성한다. 진행 상태 카드는 답변 말풍선과 분리하고 기본 접힘
상태로 유지한다. 점 애니메이션은 답변 본문 생성 전까지만 카드 아래에 표시한다.
완료된 본문이 있는 답변만 말풍선 최하단에 복사 버튼을 표시하며 Markdown
원문을 복사한다.

## 3. 결과

### 긍정적 결과

- LLM은 질문 분류와 근거 선택을 동시에 수행하지 않고 선택된 항목의 설명에
  집중한다.
- 포괄적 목록도 모든 항목을 순차적으로 완주하며 앞 조항 편향을 줄인다.
- 이전 대화 원문을 재전송하지 않고도 후속 질문의 대상을 유지한다.
- 상태, 주의 신호와 법령 원문의 의미가 섞이지 않는다.
- 법령 MCP 장애가 사용자·표준조항 설명 전체를 차단하지 않는다.
- 부분 답변과 출처를 보존한 채 긴 답변을 재개할 수 있다.

### 비용과 한계

- 고정 의도와 조문 표현을 판별하는 서버 규칙을 질문 표현 변화에 맞춰 관리해야
  한다.
- 분할 호출 수에 비례해 전체 완료 시간과 LLM 비용이 증가한다.
- `toxic_patterns`의 탐지 이유가 MCP 계약에 없으므로 개별 신호의 발생 원인을
  설명할 수 없다.
- grounding 원문은 관련 참고자료일 뿐 해당 계약에 실제 적용된다는 결론이
  아니다.
- tokenizer 실패 시 문자 수 기반 판단은 실제 토큰 수와 차이가 날 수 있다.

## 4. 검토한 대안

### 모든 질문을 한 번의 LLM 호출로 처리

채택하지 않았다. 작은 모델이 질문 분류, 대상 선택, 근거 해석과 긴 목록 생성을
동시에 수행하면서 대상 혼입과 일부 항목 누락이 반복됐다.

### 이전 대화 원문 전체를 프롬프트에 전달

채택하지 않았다. 현재 질문이 아닌 이전 질문에 다시 답하고 문맥 예산과 정보
전송 범위가 증가한다. 의미 상태 토큰으로 필요한 대상만 유지한다.

### 모든 조항 질문에 법령 grounding 호출

채택하지 않았다. 단순 내용·신호 조회의 지연과 MCP 장애 의존성이 증가한다.
법령 요청과 기록된 신호의 영향 질문에만 조회한다.

### 출력 토큰 상한 제거

채택하지 않았다. 현재 vLLM 입력·출력 합산 한도는 8,128토큰이고 긴 단일 호출은
중단, 지연과 반복 위험을 키운다. 512토큰 호출을 여러 묶음으로 완주한다.

## 5. 검증 원칙

- 질문 유형, 결과군과 조문 표현별 단위 테스트를 유지한다.
- 11개 이상 목록의 분할, 중복 없는 항목·출처와 continuation을 검증한다.
- `EXTRA`, `NO_MATCH`, `MISSING`, 빈 신호와 라벨 없는 신호를 각각 검증한다.
- 법령 `OK`와 비정상 상태에서 조항 설명 유지 여부를 검증한다.
- Markdown 안전성, 진행 카드 위치·접힘, 스트리밍 종료와 완료 후 복사를
  프런트 테스트로 검증한다.
- 기본 자동화에서는 외부 LLM·MCP 통합 테스트를 실행하지 않는다. 승인된
  비민감 fixture를 사용하는 별도 운영 검증에서만 실제 provider를 호출한다.

## 6. 재검토 조건

다음 상황에서는 이 결정을 재검토한다.

- 분할 호출의 p95 완료 시간이 운영 목표를 초과함
- 512토큰 상한 도달 또는 비정상 종료 비율이 유의하게 증가함
- 의미 상태 토큰이 후속 질문 대상을 반복적으로 잘못 복원함
- 서버의 고정 의도 규칙이 자연어 표현을 충분히 포괄하지 못함
- MCP가 주의 신호별 탐지 근거 또는 긴급도 순위를 새로 제공함
- vLLM 문맥 길이, 동시성 또는 운영 모델이 변경됨
